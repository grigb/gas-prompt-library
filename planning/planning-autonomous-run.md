Design a practical workflow and work stream that maximizes useful progress within each orchestration turn by managing sequencing, batching, parallel dispatch, dependencies, handoffs, and verification. The goal is long autonomous turns and sessions that complete as much work as possible without asking the user for permission, confirmation, or additional detail; rely on existing context, established decisions, and expert judgment, and interrupt the user only for a true block involving indispensable input, access, authority, or a materially consequential decision that cannot be resolved safely. Create a canonical orchestration plan, save it as a project document using the existing project conventions, and add the durable operating guidance—not a redundant copy of the entire plan—to the harness goal orientation. The plan must define the complete order of operations, the roadmap and critical path, dependencies and opportunities for parallel work, the workers or agents assigned to each part, the outputs and verification required, and the lowest sufficient reasoning level for each item: low, medium, or high. Use only workers and capabilities that actually exist or are already authorized; use the minimum effective number of workers, avoid unnecessary delegation layers, and do not create orchestration whose primary purpose is to manage more orchestration. Plan automation where it materially improves throughput, reliability, continuity, or recovery, including how work is dispatched, how state and outputs are preserved, and how routine failures are handled without user intervention; do not automate trivial or one-time steps when manual execution is simpler. Preserve your previously appointed role, scope, authority, and responsibilities; do not redefine or expand them. Treat elegance as a governing engineering principle and a critical, non-optional constraint: prefer the simplest coherent approach that fully satisfies the established needs, preserves quality, minimizes moving parts, dependencies, maintenance, and future rework, and introduces no abstraction, worker hierarchy, scope, artifact, or process for its own sake. Simplify the method, not the objective: do not remove, weaken, reinterpret, defer, or silently narrow established requirements, constraints, deliverables, acceptance criteria, safety boundaries, or prior user decisions. Work sequentially: define the needs, review the needs, consider the needs and their implications, examine the proposed approach, consider useful fine-tuning, and revise the plan to use the most elegant, effective, and efficient solution. Internally test every planned step against the critical path: each step must directly produce, improve, verify, or unblock a required deliverable. Remove or replace anything ceremonial, redundant, speculative, optional, unnecessarily complex, delaying, off-course, or merely restating existing artifacts, including extra approval gates, status recaps, confirmation hierarchies, blocking check-ins, excessive planning layers, and process-only work. Preserve necessary setup, integration, migration, dependency resolution, risk reduction, documentation, and verification when they materially enable or protect delivery. Create or update the required WOs from the refined plan in execution order, with each WO identifying its required outcome, dependencies, assigned worker, reasoning level, deliverable, and completion criteria. Before creating a WO, determine whether an existing WO already covers the work; update or expand the existing WO instead of creating a duplicate, and combine closely related work when it shares one deliverable or execution path. Update the WO Index so the resulting WOs reflect the refined critical-path order of operations and can be executed autonomously without further planning ceremony.
